P1 — High (fix this week)

Action 1 High Security Enable an account lockout policy (lockout is currently disabled domain-wide)Default Domain Policy — Account Lockout Policy

What was found

The exported settings report for the Default Domain Policy shows LockoutBadCount = 0 (evidence: DomainGPOs\Default Domain Policy_31b2f340.xml, Account Lockout Policy section, present in both run folders). A value of 0 means account lockout is disabled: an attacker can attempt an unlimited number of passwords against any account, online, forever. This is the 2022-era factory default — the GPO has never been modified since domain creation (ModificationTime 04/28/2022).

Why it matters

With no lockout threshold, password-spray and brute-force attacks against exposed services (SMB, LDAP, RDP, or anything federated to AD) never trip a defensive control and generate far less obvious telemetry. Combined with the 7-character minimum password length (Action 2), the domain's only real defense against online guessing is password complexity. Microsoft's security baseline for Windows Server recommends a lockout threshold of 10 or fewer invalid attempts with a 15-minute duration/reset window.

Fix — GUI path

GPMC → Forest: andrews.bz → Domains → andrews.bz → Group Policy Objects → Default Domain Policy → right-click → Edit → Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies → Account Lockout Policy. Set: Account lockout threshold = 10 invalid logon attempts; accept the prompted defaults of Account lockout duration = 15 minutes and Reset account lockout counter after = 15 minutes (adjust to your standard). On Server 2022 you may also see Allow Administrator account lockout — enable it to cover the built-in Administrator over the network.

Fix — PowerShell path

Backup-GPO -Name 'Default Domain Policy' -Path C:\GPOBackups

Takes a restorable backup of the GPO (AD object + SYSVOL folder) before any change.

net accounts /lockoutthreshold:10 /lockoutduration:15 /lockoutwindow:15

Run on DC01: writes the lockout values into the domain account policy, which lives in the Default Domain Policy. There is no Set-GP* cmdlet for security-settings INF values; net accounts (or editing the GPO in GPMC) is the supported path.

gpupdate /force

Forces immediate policy reprocessing on the machine you run it on; other members pick it up within the 90–120 min refresh cycle.

Pre-change safety

Backup-GPO -Name 'Default Domain Policy' -Path C:\GPOBackups first (command above). Log the change with the before-values: threshold 0 / duration n-a / window n-a. Warn the helpdesk: a too-aggressive threshold can create a self-inflicted denial of service if a device with a cached stale password hammers a DC.

Verification

net accounts on DC01 should report Lockout threshold: 10. Re-run Invoke-GPOAudit.ps1 and confirm the Default Domain Policy ComputerDSVersion incremented in DomainGPOs\DomainGPOInventory.csv. Watch Security event 4740 (account locked out) to confirm the control fires during a deliberate test with a scratch account.

Rollback

Restore-GPO -Name 'Default Domain Policy' -Path C:\GPOBackups — restores both the AD version and the SYSVOL content, or simply run net accounts /lockoutthreshold:0 to revert the single value.

Traceability: Analyst finding A1 — derived from per-GPO settings XML; not present in Findings.csv (the tool audits GPO plumbing, not setting values).

P2 — Medium (fix this month)

Action 2 Medium Security Raise the password policy from 2022 factory defaults (minimum length 7)Default Domain Policy — Password Policy

What was found

The Default Domain Policy carries the untouched installation defaults (evidence: DomainGPOs\Default Domain Policy_31b2f340.xml): MinimumPasswordLength = 7, MaximumPasswordAge = 42, PasswordHistorySize = 24, PasswordComplexity = true, ClearTextPassword = false (reversible encryption correctly off).

Why it matters

Seven characters is below every current guideline: the Microsoft security baseline sets 14, CIS Benchmarks set 14, and NIST SP 800-63B sets 8 as an absolute floor with length preferred over forced rotation. A 7-character minimum makes offline cracking of captured NTLM hashes (and Kerberoasted service-account tickets) trivial on commodity GPUs. The 42-day forced rotation is also a legacy pattern — modern guidance pairs longer minimums with rotation only on evidence of compromise.

Fix — GUI path

GPMC → Group Policy Objects → Default Domain Policy → Edit → Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies → Password Policy. Set Minimum password length = 14. Decide your rotation stance deliberately: either keep 42 days or move toward long-lived passphrases per NIST — document whichever you choose. Leave complexity enabled and history at 24.

Fix — PowerShell path

Backup-GPO -Name 'Default Domain Policy' -Path C:\GPOBackups

Restorable pre-change backup (skip if already taken in Action 1 the same day).

net accounts /minpwlen:14

On DC01: raises the domain minimum password length inside the Default Domain Policy.

Get-ADDefaultDomainPasswordPolicy

Reads the effective domain password policy straight from the domain head object — your verification source of truth.

Pre-change safety

Backup as above. Communicate before enforcing: existing passwords are NOT invalidated by the change; users are only held to 14 characters at their next change, so plan a phased notice. Check for service accounts with short passwords that scripts might reset.

Verification

Get-ADDefaultDomainPasswordPolicy shows MinPasswordLength 14. Re-run the audit; the inventory row for Default Domain Policy should show a bumped Computer version.

Rollback

Restore-GPO -Name 'Default Domain Policy' -Path C:\GPOBackups or net accounts /minpwlen:7.

Traceability: Analyst finding A2 — derived from per-GPO settings XML.

Action 3 Medium Connectivity Investigate public IP addresses returned for the AD domain apex nameandrews.bz DNS zone (domain apex)

What was found

Both connectivity captures show the domain name resolving to four addresses: Summary\ConnectivityTests.csv → “DNS resolution, andrews.bz: Resolved 192.168.111.5, 192.168.111.6, 199.181.197.11, 199.181.197.12.” The 192.168.111.x pair are the DC-registered apex A records; the 199.181.197.x pair are public Internet addresses that should not normally exist inside an AD-integrated zone.

Why it matters

Domain members use the apex name for DFS paths like \\andrews.bz\SYSVOL. If a client round-robins onto a public address, SYSVOL/NETLOGON access and Group Policy processing can fail intermittently (classic events 1058/1030) even though everything looks healthy most of the time. It can also leak internal SMB/LDAP connection attempts to an external host. Common causes: someone manually added the public web-site IPs to the internal zone so http://andrews.bz works inside the LAN, or clients are resolving via an external resolver. Note the current event logs show zero 1058/1030 errors, so this is preventive — but it is a latent reliability trap.

Fix — GUI path

DNS Manager on DC01 → Forward Lookup Zones → andrews.bz → sort by Name and inspect the “(same as parent folder)” A records. Expected: one per DC (192.168.111.5/.6, assuming both are DCs). If 199.181.197.11/.12 appear here, they were added manually — remove them and publish the website internally via a dedicated host record (e.g., www.andrews.bz) instead. Also verify member NIC DNS settings point only at internal DCs.

Fix — PowerShell path

Get-DnsServerResourceRecord -ZoneName 'andrews.bz' -ComputerName DC01 -RRType A | Where-Object HostName -eq '@' | Format-Table HostName,RecordData

Lists every apex A record in the AD zone so you can see exactly where the public IPs come from.

Resolve-DnsName andrews.bz -Server 192.168.111.5

Queries the DC's DNS service directly, removing client-side resolver ambiguity.

Remove-DnsServerResourceRecord -ZoneName 'andrews.bz' -ComputerName DC01 -RRType A -Name '@' -RecordData '199.181.197.11'

Removes one stray apex record (repeat for .12) — run ONLY after confirming they are manual additions and nothing internal depends on them.

Pre-change safety

Export the zone first: Export-DnsServerZone -Name andrews.bz -FileName andrews.bz.bak (writes to %windir%\system32\dns). Confirm no internal service intentionally depends on the apex resolving to the public web host.

Verification

Resolve-DnsName andrews.bz from a member returns only DC addresses. Re-run the audit — ConnectivityTests should list only 192.168.111.x. Monitor GP operational log for absence of 1058/1030.

Rollback

Re-add the records with Add-DnsServerResourceRecordA -ZoneName andrews.bz -Name '@' -IPv4Address 199.181.197.11 (and .12), or restore from the zone export.

Traceability: Analyst finding A3 — correlated from ConnectivityTests.csv in both runs.

Action 4 Low Security Inspect the four “GpoCustom” ACL entries and confirm they match factory defaultsDefault Domain Policy; Default Domain Controllers Policy

What was found

The tool flagged 4 findings (2 GPOs × 2 trustees): Permissions\GPOPermissions.csv shows Domain Admins and Enterprise Admins with Permission=GpoCustom on both default GPOs, Inherited=False, Denied=False. GpoCustom only means the ACE set does not collapse into one of the five named permission levels that Get-GPPermission can express.

Why it matters

On the two default GPOs this exact pattern IS the out-of-box state: Domain/Enterprise Admins receive Edit-Delete-Modify-Security without the Apply right (so admin workstations aren't force-fed the GPO), which the cmdlet renders as Custom. The risk being screened for is that Custom can also hide a Deny ACE or an Apply-without-Read combination that silently breaks processing — so it warrants one manual look, then a documented pass. All remaining ACEs are textbook: SYSTEM = full edit, Authenticated Users = Read+Apply, Enterprise Domain Controllers = Read (the MS16-072 read requirement is satisfied — no read gaps exist).

Fix — GUI path

GPMC → Group Policy Objects → Default Domain Policy → Delegation tab → Advanced… → select Domain Admins → confirm Allow on Read/Write/Create/Delete child objects and no Deny entries anywhere in the list; Advanced → Effective Access can prove it. Repeat for Enterprise Admins, then for Default Domain Controllers Policy. If it matches defaults, record “verified default ACL” in the GPO description (Action 8).

Fix — PowerShell path

Get-GPPermission -Name 'Default Domain Policy' -All | Format-Table Trustee,Permission,Inherited

Re-lists the delegation exactly as the audit captured it.

(Get-GPO -Name 'Default Domain Policy').GetSecurityInfo() | Format-List

Dumps the raw ACEs behind the 'Custom' label so you can eyeball Deny bits and access masks without GPMC.

Pre-change safety

Read-only verification — no backup required. If you DO find a Deny ACE or Apply-without-Read, stop, back up with Backup-GPO, and treat the correction as a new change ticket.

Verification

No Deny ACEs present; ACL matches the documented default. On the next audit run these four Low findings remain (the tool cannot see your verification) — the GPO description note is the closure evidence.

Rollback

Not applicable for verification. If ACEs were modified, Restore-GPO from the backup.

Traceability: Merges 4 Findings.csv rows: “Custom ACL on … for Domain Admins / Enterprise Admins” (both GPOs, both runs = 8 raw rows).

Action 6 Low Processing Review recurring warning 6314 (bandwidth estimation failed, assuming fast link)DC01 and W2022 — GP operational log

What was found

EventLogs\GroupPolicyEvents.csv: warning 6314 appears 161× on DC01 and 170× on W2022 — every refresh cycle in the captured window. It is the only non-informational event in either log. All timing events (8000/8001/8006/8007) complete in 0 seconds; there are no 7000-series processing errors and no 1058/1030 SYSVOL errors.

Why it matters

6314 means the GP engine could not measure link speed (typical on virtual NICs and when NLA can't sample), so it assumes a fast link — which on a wired/virtualized LAN is the correct outcome, and the “slow link threshold: 500 kbps / connected over slow link: No” lines in RSOP\gpresult-R.txt confirm nothing is being skipped. It is noise here, but on VPN laptops the same assumption can force software-install/folder-redirection processing over slow links. Fix it only if you want clean logs or have remote clients.

Fix — GUI path

Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-GroupPolicy/Operational';Id=6314} -MaxEvents 5 | Format-List TimeCreated,Message

Confirms the warning content and cadence on any machine you're checking.

If setting the policy, back up the GPO you edit first (Backup-GPO).

Action 10 Optional Security Deploy security baseline GPOs and Windows LAPS (the domain runs on defaults alone)Domain-wide

What was found

DomainGPOs\DomainGPOInventory.csv: exactly 2 GPOs exist — the two defaults — with no preferences, scripts, drive maps, printers, or software-install extensions anywhere, and zero WMI filters (WMI-Filters\WMIFilters.csv: no records). Every hardening decision in this domain is currently “whatever shipped in the box.”

Why it matters

Defaults leave large gaps a baseline closes: SMB signing/encryption posture, NTLM restrictions, LSA protection, advanced audit policy, PowerShell logging, and local-admin password randomization. Windows LAPS is built into Server 2022 (April 2023 update onward) and eliminates the shared-local-admin-password lateral-movement path — it is also the modern replacement for the GPP-cpassword pattern this tool hunts for (none found here, per the “No cpassword values found” log line — that check PASSED).

Fix — GUI path

Download the Microsoft Security Compliance Toolkit; import the Server 2022 Member Server and DC baselines as NEW, separate GPOs (never merge into the defaults); link Member Server baseline to a staged OU first, DC baseline to the Domain Controllers OU after testing. For LAPS: extend the schema, then create a “LAPS – Servers” GPO under Computer Configuration → Policies → Administrative Templates → System → LAPS.

Fix — PowerShell path

Import-GPO -BackupGpoName 'MSFT Windows Server 2022 - Member Server' -Path C:\Baselines -TargetName 'SEC-Baseline-MemberServer' -CreateIfNeeded

Imports the toolkit baseline into a fresh GPO so the defaults stay untouched and rollback is a link removal.

Update-LapsADSchema; Set-LapsADComputerSelfPermission -Identity 'OU=Servers,DC=andrews,DC=bz'

One-time Windows LAPS schema extension, then grants machines in the OU the right to write their own rotated password.

New-GPLink -Name 'SEC-Baseline-MemberServer' -Target 'OU=Servers,DC=andrews,DC=bz' -LinkEnabled Yes

Links the baseline where it applies; precedence over the domain-linked defaults is automatic at the OU level (LSDOU).

Pre-change safety

Back up ALL GPOs first (Action 11 script). Stage on a pilot OU with one server for at least one refresh cycle before broad linking. Baselines can break legacy protocols — test SMB/NTLM-dependent apps.

Verification

gpresult /r on a pilot machine lists the baseline GPO under Applied; re-run the audit and confirm the new GPOs appear linked, versioned, and with clean permissions.

Rollback

Remove-GPLink -Name 'SEC-Baseline-MemberServer' -Target 'OU=Servers,DC=andrews,DC=bz' — unlinking reverts scope instantly without deleting the GPO.

7Best practices & hardening guide

The P4 actions above (8–11) are the forward-looking program. Sequencing recommendation for a defaults-only domain: descriptions + central store first (zero risk, enables everything), then baseline GPOs staged on a pilot OU, then LAPS, with backup automation switched on before the first baseline link goes live. Adopt a quarterly Invoke-GPOAudit.ps1 cadence — diff Findings.csv between runs as your drift detector — and alert on GP operational events 7000–7017, 1058/1030, and 1054/1055 (Action 11 gives the exact filter). Keep the two default GPOs reserved for what they are: account policy (DDP) and DC user-rights/audit (DDCP); everything new goes in purpose-named GPOs (suggested convention: SEC-|APP-|USR-<Scope>-<Purpose>) so security intent is legible in GPMC at a glance.

H. Glossary

LSDOUGroup Policy processing order — Local, Site, Domain, OU. Later wins on conflicts; link order breaks ties within a container (lower number = higher precedence).
RSOPResultant Set of Policy — the computed union of everything that actually applied to a specific computer/user, as captured by gpresult and the RSOP WMI provider.
Enforced vs. Block InheritanceBlock Inheritance stops higher-level links at an OU; an Enforced link punches through the block AND wins conflicts against lower-level GPOs. Neither is in use here.
MS16-0722016 security change: computers read GPOs with the machine account, so every GPO must grant Read to Authenticated Users or Domain Computers or it silently stops applying. Verified satisfied in this domain.
cpasswordThe AES-encrypted password field in legacy Group Policy Preferences XML. Microsoft published the static key (MS14-025), so any cpassword is a plaintext-equivalent credential. Scan result here: clean.
GpoCustomGet-GPPermission’s label for any ACE set that doesn’t match its five canonical permission levels — includes the factory-default admin ACEs on default GPOs, but can also hide Deny entries; hence Action 4.
DFSRDFS Replication — the service that replicates SYSVOL between DCs. Single-DC domains (like this one appears to be) have no replication partner, so AD↔SYSVOL version deltas are the main consistency check.
Central StoreA SYSVOL folder (Policies\PolicyDefinitions) holding one authoritative ADMX/ADML set so every GPMC console renders identical Administrative Templates.
Windows LAPSBuilt-in local-admin password rotation storing per-machine secrets in AD with ACL-gated retrieval — the modern replacement for the GPP-password anti-pattern.
